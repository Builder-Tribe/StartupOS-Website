# Database

> Truth source: `trippy/server/src/db.ts` (full DDL + migrations) and `src/seed.ts` (demo data).
> One canonical SQLite database serves all four surfaces. Update this file with every schema change.

## Engine & location

- SQLite via Node's built-in **`node:sqlite`** — requires `NODE_OPTIONS=--experimental-sqlite`
  (already set in every npm script; don't remove it).
- Dev path: `trippy/server/data/trippy.db` (gitignored — **contains real accounts; never delete
  or `reset-db` without explicit consent**). Override with `TRIPPY_DB_PATH` (tests use a temp file;
  production uses `/var/data/trippy.db` on a Render persistent disk).
- Schema is created on boot; `seedIfEmpty()` populates demo data idempotently (guarded per domain,
  so partner/admin seeds apply even on an existing consumer DB).

## Conventions

- Ids: TEXT, generated by `uid()` in `db.ts`. Columns: `snake_case`. Timestamps: TEXT via
  `datetime('now')` (UTC). Dates: TEXT `YYYY-MM-DD`.
- List/object fields are **JSON-encoded TEXT** columns — write with `j(value)`, read with
  `pj<T>(text, fallback)`. Don't add join tables for simple lists.
- Booleans are INTEGER 0/1.
- **Migrations are additive and in-place**: `CREATE TABLE IF NOT EXISTS` for new tables; for new
  columns on existing tables, follow the guarded `ALTER TABLE` pattern at the bottom of `db.ts`
  (check `PRAGMA table_info`, add if missing). Never drop or rewrite user data.

## Tables by domain (43)

### Consumer / social
| Table | Purpose |
|---|---|
| `users` | Traveller accounts: auth (scrypt `password_hash`/`salt`), profile, personality, trust, `status`; JSON columns `past_trips` + `socials` (trust pack) |
| `trips` | A traveller's upcoming travel plan (destination + date window) — the matching input |
| `connections` | Travel requests; mutual accept unlocks chat |
| `chats`, `chat_members`, `messages` | 1:1 + group messaging (clients poll) |
| `reports`, `blocks` | Safety: user reports and blocks |
| `id_verifications` | Government-ID verification requests: doc type + last-4 only (never the full number), pending → approved/rejected by an admin (`reviewed_by`), reject reason shown to the traveller |
| `vouches` | Community trust: one changeable vouch per (from_user, to_user) pair, rating 1–5 + note + the shared `group_id`; `users.trust_score`/`trust_reviews` recomputed from these |
| `groups`, `group_members`, `itinerary_items` | DIY groups **and trip hubs** + shared itinerary. A hub is a group linked to its source trip via `source_type` (`partner`/`operator`) + `source_id`; `invite_code` powers `/join/:code` links; first joiner gets `role='leader'` (see `lib/hubs.ts`) |
| `polls`, `poll_votes` | Trip Hub polls — options JSON on the poll; one row per voter (`PRIMARY KEY (poll_id, user_id)`, upsert on re-vote) |
| `bike_profiles`, `car_profiles` | Rider & driver vehicle details (type, CC, experience level, seating capacity, AC, driving bio) for companion & carpool matching |
| `adventure_routes` | Bike ride & road trip routes linked to DIY `groups` hubs (`mode`, cities, waypoints JSON, seats, cost) |
| `ride_location_pings`, `ride_checkins` | Real-time member location updates & manual waypoint check-in log on active adventure routes |
| `carpool_requests` | Seat requests from co-travellers on road trip routes (pending → accepted/declined; accepted joins hub) |
| `otps`, `email_verifications` | **Legacy** — phone OTP (never launched) and the removed email-verification flow. Kept for data continuity; do not build on them without checking the PRD |

### Catalogue / discovery
| Table | Purpose |
|---|---|
| `destinations` | Curated destinations incl. the DIY cost model (hostel/food/transport/activities) |
| `group_trips` | Simulated external-operator departures (Phase-2 aggregator placeholder) |
| `hostels`, `hostel_reviews`, `hostel_stays` | Canonical hostel (Property) entity; `source='user_submitted'` rows are traveller-owned — `created_by_user_id TEXT REFERENCES users(id)` (added via migration guard) controls privacy (only visible to creator), edit (`PUT /hostels/:id`), and delete (`DELETE /hostels/:id`). `propertyType` enum: `hostel`, `airbnb`, `hotel`, `homestay`. |

### Partner CRM (multi-tenant)
| Table | Purpose |
|---|---|
| `partner_orgs` | Tenant: travel community/host org |
| `partner_admins` | Partner users (separate auth realm from consumers) |
| `partner_trips` | Hosted trips; lifecycle `draft → published → …` via `status` (+ effective status logic in `lib/trips.ts`); `payment_url` is the external booking link |
| `trip_itinerary_days`, `trip_media`, `trip_tags`, `trip_categories` | Trip content |
| `trip_outbound_clicks` | Booking-intent analytics (who clicked Book Now, when, from where) |
| `bookings` | Bookings backbone: traveller `claimed` → partner `confirmed`/`rejected` (or traveller `cancelled`); one active booking per (trip, user); claims + confirms both hold seats against `max_group_size` |
| `waitlist` | Full-trip waitlist; `notified` flips when a freed seat pings the traveller |
| `notifications` | In-app notifications (booking decisions, waitlist spots); future push pipeline reads from here |

**Isolation rule:** every partner-facing query filters by `org_id`. Cross-org reads exist only in
the Admin Console.

### Admin / platform
| Table | Purpose |
|---|---|
| `admin_users`, `admin_roles`, `admin_permissions`, `admin_role_permissions`, `admin_user_roles` | RBAC catalogue — roles/permissions are **data**, editable from the console (see [auth.md](auth.md)) |
| `admin_audit_logs` | **Immutable** action log — insert-only; no update/delete code paths exist, and none may be added |
| `internal_notes` | Ops notes attachable to any entity (`entity_type` + `entity_id`) |
| `sessions` | Server-tracked admin sessions (revocable) + traveller session revocation |
| `login_events` | Login history for travellers/admins (device/browser/OS) |
| `status_history` | Entity status transitions with actor + reason (who suspended what, when, why) |

## Seed data (`seed.ts`)

Idempotent blocks run in this order:

1. **Consumer catalogue** — destinations, 35 hostels, 29 `group_trips`, ~18 demo travellers with trips/stays/reviews.
2. **Real partner communities** (`seedRealCommunities`) — 6 authentic travel operators seeded with real scraped trips, each with a `@partner.trippy` admin credential:
   - **Adventure Buddha** (`adventurebuddha@partner.trippy`) — 3 treks (Kedarkantha, Kanatal, Chopta)
   - **Tripper Trails** (`trippertrails@partner.trippy`) — 3 adventure trips
   - **Plan the Unplanned** (`plantheunplanned@partner.trippy`) — 7 domestic/international trips
   - **Zostel Trips** (`zosteltrips@partner.trippy`) — 3 Zostel-curated group trips
   - **WanderOn** (`wanderon@partner.trippy`) — 3 pan-India group trips
   - **Tripbae** (`tripbae@partner.trippy`) — 3 South India weekend trips
3. **Founder account** (`seedFounderAccount`) — idempotent: Harshit's consumer, admin (FOUNDER + SUPER_ADMIN), and partner org (`trippy-official` / `Trippy Official & Host Community`) created on every boot.
4. **Demo consumer** — `traveller@trippy.test` / `Traveller@123`.
5. **Admin RBAC** — 8 role-named admin users (test env only) + hostel lifecycle variety.

> `seedPartnersIfEmpty` (dummy placeholder orgs: Himalayan Wolves, Coastal Nomads etc.) only runs in `TRIPPY_TEST=1` environments to satisfy partner auth tests. These are not created in dev/prod.

Demo logins are listed in the root [README](../README.md).

> Testing gotcha: seeded rows share one `created_at` second, so "find entity on page 1" breaks —
> query with an explicit large `pageSize` or a search filter in tests (see [testing.md](testing.md)).

## Planned evolution

SQLite → PostgreSQL/Supabase is a designed seam: all access goes through `db.prepare` parameterized
SQL in one process, and the schema lives in a single file. Don't introduce an ORM or a second data
store as a side effect of a feature; see [decision-log.md](decision-log.md).
