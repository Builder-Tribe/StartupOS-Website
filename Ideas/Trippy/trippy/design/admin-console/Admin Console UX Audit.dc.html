03 — Critical fixes

Top 5 P0 issues — detailed fix spec

1
Add bulk actions to all list views
P0DataTable in ui.tsx · all list pages
Every list view (Partners, Trips, Hostels, Travellers, Admin Users) requires bulk actions. A support agent reviewing 30 spam reports, or a partner manager approving 8 pending partners, or a trip reviewer suspending 5 flagged trips — all of these must be completable without clicking into each row individually. Currently zero bulk actions exist anywhere.
Fix: Add a checkbox column to every DataTable as the first column. When ≥1 rows are checked, a floating "bulk actions bar" appears above the table: "X rows selected · [Action buttons]." Actions vary by entity type: Partners → Activate / Suspend · Trips → Publish / Suspend / Feature / Archive · Travellers → Suspend / Reactivate · Admin Users → Deactivate. All bulk destructive actions trigger a single ConfirmDialog: "This will affect X [entity type]. Enter a reason." The reason is applied to each audit log entry. The DataTable columns prop gains a selectable: true flag that activates the checkbox column.
2
Add date range, action type & actor filters to audit logs + CSV export
P0AuditLogs.tsx · DataTable filters array
AuditLogs.tsx defines exactly 1 filter — resourceType. There is no date range picker, no action type filter, no admin actor filter, and no export. The audit log is the primary forensic tool for the Trippy team — "who did what and when" is unanswerable without these filters. An investigation into a partner suspension needs: actor filter ("[email protected]") + action filter ("partners.suspend") + date range ("last week").
Fix: Add 4 filters to AuditLogs: (1) Date range picker (from/to date, defaults to last 30 days). (2) Action type — derived from the distinct action values in the API: partner.activate, partner.suspend, trip.publish, trip.suspend, traveller.suspend, session.revoke, role.update, etc. (3) Admin actor — a searchable select from active admin accounts. (4) Resource type (already exists). Add a "Export CSV" button to the DataTable extraControls slot — hits /audit-logs/export?{query}. The exported CSV includes all columns including the before/after state (which is in the DB but not currently shown in the UI — add it as a "Changes" column).
3
Add ConfirmDialog to Roles permission saving — blast radius is every user of that role
P0Roles.tsx · save() function · no confirmation
Roles.tsx save() calls aapi.put('/roles/:id/permissions') directly when the "Save" button is clicked. This immediately modifies the permissions for every admin user assigned to that role — potentially dozens of people. A SUPPORT_AGENT who accidentally has their role's permissions changed mid-session could gain (or lose) the ability to take destructive actions without warning. This is a high-blast-radius action with zero friction.
Fix: Before the aapi.put() call, show a ConfirmDialog: title "Update [Role Name] permissions", message "This will immediately affect [N] admin user(s) assigned this role: [comma-separated names]. They may gain or lose access to actions in the console." With a mandatory reason field (recorded in audit_logs). On confirm, proceed with the save. The audit log entry for a role permission change should include the before/after permission diff — not just "role.update."
4
Add keyboard shortcut (Cmd+K) and keyboard navigation to global search
P0AdminApp.tsx · GlobalSearch component
GlobalSearch exists in the topbar and works, but requires a mouse click to focus. High-volume admins (partner managers reviewing 20 partners in a session) should be able to jump to any entity in 2 keystrokes: Cmd+K to open search, type, Enter to navigate. Currently this requires: mouse move → click search input → type → mouse click on result. 4 interactions vs 2.
Fix: Add a useEffect with a global keydown listener: (e.metaKey || e.ctrlKey) && e.key === 'k' → focus the search input. Add ↑/↓ keyboard navigation through results and Enter to navigate to the highlighted result. Add Escape to clear and close. Show a ⌘K hint in the search input placeholder. Show "No results for '[query]'" when the API returns an empty array — currently the dropdown simply disappears, which looks like a loading state.
5
Gate partner user deactivation with ConfirmDialog + reason
P0PartnerDetail.tsx · userAction() · immediate API call
In PartnerDetail.tsx, the "Deactivate" button on a partner user calls userAction(u.id, 'deactivate') instantly with no confirmation. This immediately revokes the partner user's access to the Partner CRM. If an admin mis-clicks (a realistic scenario given the table layout where Activate/Deactivate buttons appear in every row), they've locked out a legitimate partner operator with no warning and no reason recorded.
Fix: Replace the direct userAction call with a ConfirmDialog: title "Deactivate [user name]", message "This removes their access to [Org Name]'s Partner CRM immediately. They won't be able to manage trips until reactivated." With a required reason field. The reason is written to audit_logs as partner_user.deactivate. Same pattern for the Activate action (non-destructive, but should still be logged with a reason for audit completeness).

09 — Sensitive action confirmation

Universal confirmation dialog for destructive actions

Two tiers: Standard ConfirmDialog (reversible actions — suspend, archive) and HighRiskDialog (irreversible — offboard partner, permanently close hostel). Both require a reason. Both write to audit_logs.

Standard ConfirmDialog — "Suspend Himalayan Wolves"
Suspend Himalayan Wolves?
This will immediately:
• Remove all their trips from Trippy search results
• Block their admin users from logging into the Partner CRM
• Stop all new booking clicks to their payment links

The partner can be reactivated at any time.
⚠ This action will be recorded in the audit log — your name, timestamp, and reason will be permanently visible to other admins.
Reason (required)
Multiple traveller complaints about booking fraud — investigating
This action is logged and cannot be undone without a separate reactivation action.

Permanently offboard Himalayan Wolves?
This action is irreversible. Offboarding will:
• Permanently remove all their trips from Trippy
• Revoke all admin access for all their users
• Delete their organisation from the platform

This cannot be undone. A new signup would be required to re-list.
⛔ This permanently deletes the partner from the platform. There is no undo.
Type "Himalayan Wolves" to confirm

Design rules for all confirmation dialogs
1. Always show blast radius: List what will be affected (N trips removed, N users locked out) — not a generic "are you sure?"
2. Reason field is always required for any action that modifies a status (suspend, archive, deactivate, revoke). Optional only for constructive actions (activate, feature).
3. Audit log warning is always shown: "This action will be recorded in the audit log with your name and timestamp." This reminds admins they are accountable.
4. HighRiskDialog requires entity name typing for: offboard partner, permanently close hostel, revoke all sessions for a traveller, delete admin user. These are the 4 irreversible actions.
5. Cancel is always the default focus. Confirm button is never focused on dialog open — the admin must consciously move to it.
6. Dialog overlay blocks the entire UI. No accidental clicks through the backdrop.
10 — Design checklist

20-point admin-specific pre-handoff validation

RBAC (4 checks)
1
Nav items are hidden — not disabled — for roles without the required permission. A SUPPORT_AGENT should never see a greyed "Partners" nav item; it should not exist in their DOM.
2
Action buttons are hidden — not disabled — when the admin lacks the permission. A READ_ONLY_ADMIN should see no Suspend, Activate, or Edit buttons anywhere. Use the Can component.
3
SUPER_ADMIN role is immutable. No edit button appears on the SUPER_ADMIN role card in the Roles page. Server enforces this too, but the UI must never show a misleading edit affordance.
4
Global search results are permission-scoped. Search results only include entity types the admin has *.view permission for. Never leak a partner name to a SUPPORT_AGENT who lacks partners.view.
Audit accountability (5 checks)
5
Every destructive action shows a ConfirmDialog with blast radius description, mandatory reason field, and audit log warning. No status-changing action fires without a confirmation.
6
Irreversible actions use HighRiskDialog (entity name typing required). Offboard partner, permanently close hostel, revoke all traveller sessions, delete admin user.
7
Audit log is visually immutable. Lock icon on each row. No edit/delete controls. No row-hover action buttons. "Cannot be edited or deleted" in the page header.
8
Role permission changes trigger a ConfirmDialog showing the number of affected admin users and requiring a reason. The audit entry shows the full permission diff (before/after).
9
Audit log has date range + action type + actor filters and CSV export. An admin must be able to answer "who suspended this partner on Tuesday?" within 30 seconds.
Data safety (3 checks)
10
Passwords, hashes, tokens are never exposed. No view in the admin console — not Traveller detail, not Admin Users, not audit logs — ever renders a password, bcrypt hash, JWT token, or raw API key.
11
CSV exports exclude sensitive columns. Traveller exports never include password hashes. Audit log exports include IP addresses only when the admin has the audit_logs.export permission (a separate permission).
12
Hostel publish shows canonical source warning. "Publishing this hostel makes it immediately visible to all Trippy travellers." Admin must acknowledge before publishing.
Efficiency (4 checks)
13
Bulk actions exist on all list views. Any entity type that can be suspended/activated/archived must support bulk selection + bulk action. An admin should never need to click into individual rows to perform the same action on 10 items.
14
Cmd+K opens global search from anywhere. ↑/↓/Enter keyboard navigation through results. Escape to close. No mouse required to search and navigate.
15
Platform health badges in sidebar. Admin knows at a glance which entity type needs attention without navigating to the dashboard first. Amber = actionable; red = urgent.

URL-persisted filters. An admin who filters Trips by "suspended + missing payment" can share or bookmark that URL. Returning to the same URL restores the exact filter state. DataTable already does this ✓.
Visual distinction from consumer app (4 checks)
17
Dark sidebar is always visible. The #14202a sidebar with teal active state immediately communicates "this is the admin console, not the consumer app." It must never be removed or replaced with a light sidebar.
18
"Trippy Admin" branding in the sidebar. The sub-label below the logo reads "Admin" — never just "Trippy." A confused admin should instantly know which portal they're in.
19
Destructive action buttons use the danger style (red background/text, red50 background) — never teal or coral. Teal is the consumer app's trust color; using it for destructive admin actions would create dangerous visual confusion.
20
Admin role is always visible in the topbar. The current user's role label ("Super Admin", "Support Agent") is shown next to their name in the topbar at all times. Admins should always know what permissions they're operating with.
