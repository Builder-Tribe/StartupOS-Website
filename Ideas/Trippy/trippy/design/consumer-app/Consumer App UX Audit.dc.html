03 — Critical fixes

Top 5 P0 issues — detailed fix spec

Each fix spec includes: what to change, where in the code, why it matters for the user.

1
Remove auth gate from discovery — browsing must work without an account
P0App.tsx · line 98 — `!user` → Login redirect
The entire app routes to Login when unauthenticated, except /trip/:slug. A visitor who lands via Instagram ad and wants to browse group trips hits a login wall immediately — the single biggest drop-off point. This directly violates PRD rule: "Do NOT gate browsing behind signup."
Fix: Add public routes for / (Landing), /search (Results), /trip/:slug (already done), and /hostels. Wrap these in a PublicShell (already exists for trip pages) with a "Sign in to connect" CTA in the topbar. Matching, chat, and DIY group creation remain auth-gated. Add a "Sign in to see your matches" nudge at the top of the Matches section when browsing as guest.
2
Add mobile bottom nav — the topnav is unusable on Android at 375px
P0App.tsx · ConsumerApp shell · topnav
The current navigation is a horizontal topbar with text links (Matches, Requests, Chats, Hostels). On a 375px Android screen this is 5 links in ~180px of space — tiny touch targets, wrapping on smaller screens, and completely hidden on the Landing page. DIY has no nav entry at all. The product rule says "Do NOT hide features on mobile that are available on desktop."
Fix: Replace topnav with a 5-tab bottom nav: Discover (compass) · Matches (users, badge for new matches + requests) · + (floating coral CTA — opens DIY path or trip search) · Chats (chat-circle, unread badge) · Profile (user-circle). Keep topbar for logo + notification bell only. On desktop/web, keep the topnav. Bottom nav safe area: 83px iOS / 48px Android.
3
Add chat locked state + report/block within 2 taps of any profile
P0ChatThread.tsx · UserProfile page · missing screen
Chat is technically gated (only accessible post-mutual-connect), but there's no visible locked state. A user viewing another traveller's profile sees no indication that "chat unlocks when you both connect." This breaks trust — the system feels arbitrary. Separately, there is zero report/block affordance anywhere in the app. The PRD rule "Report/block must work within 2 taps from any profile view" is completely unimplemented.
Fix (chat lock): On UserProfile, if connection status is not 'accepted', show a greyed chat preview card: "💬 Chat unlocks when you both connect" with a lock icon. On accepted, show "Open chat" teal button. Fix (report/block): Add a "⋯" overflow menu to every UserProfile and match card. Tap → bottom sheet with "Report this person" + "Block [name]". Report opens a 2-field form (reason + optional note). Both must complete in 2 taps from profile. Block immediately removes the person from all lists.
4
Compatibility score must always show AI explanation — never a bare number
P0Matches.tsx · ScorePill component · `.reasons` class
The `reasons` array exists in the API response and is rendered in `.reasons` class — but it appears as "✨ reason1 · reason2" with no framing. The PRD rule says compatibility score must show with "a brief AI explanation — never a bare number." Currently on the match card the score pill (e.g. "84% match") appears disconnected from the reasons below it. On compact views (DIY people step), only the score pill appears with no reasons at all.
Fix: Rename the reasons block to an AI insight component. Format as: Score pill + below it in teal text: "Because you both [reason1] and [reason2]." Use sentence case, not a dot-separated list. On compact cards (DIY people step), show the top 1 reason inline below the score: e.g. "84% · Both love trekking." Add a "?" tap on the score pill that expands a tooltip with all 3–5 reasons. This transforms the score from a black-box number into a trust signal.
5
Onboarding must create an upcoming trip + reveal Travel Personality Score
P0Onboarding.tsx · 4-step wizard · missing step 4
The onboarding wizard (4 steps) completes with bio + emergency contact — but the user arrives in the app with no upcoming trip set. Matching is silent ("No travelers found" empty state) until a trip is set. The user doesn't understand why — dead end. Additionally, after completing the profile, there's no Travel Personality Score reveal moment. The PRD specifies this should be "a moment of delight." Currently `user.personality` is just a text label shown on profile with no reveal.
Fix: Add step 5 to onboarding: "Where are you headed next?" — destination picker + date range (can be marked flexible). This creates a trip via POST /trips and immediately activates matching. Fix (personality reveal): After step 5, show a full-screen reveal card: "Based on your travel style, you're a [PERSONALITY TYPE]" with an icon, color, and 2-line description. Animate the type label appearing letter by letter. Include "See your first matches →" CTA to go directly to Matches.
04 — Revamp briefs

7 core user jobs — happy paths + edge cases

1
Search-first discovery — find trips for a destination + dates
Happy path
Land on / → see searchbar → pick destination + dates → tap "Search trips" → Results page with hosted trips + DIY rail → tap a trip to see detail → tap "Book Now" → redirects to partner's payment page.
Edge cases
No trips for destination+dates → empty state with "Be the first — start a DIY trip" + 3 nearby dates that have trips. Dates in the past → inline validation "Start date can't be in the past." Date range too short (<2 days) → "Most trips need at least 3 days — adjust your dates?"
Key components
SearchBar · TripCard (hosted) · DIYRail · EmptyTrips · AvailabilityChip · BookNowButton (external link tracker)
Improvements
Sort/filter Results: by price (low-high), dates (soonest), operator rating. Sticky Book Now: floating bottom bar on Trip Detail mobile. "X Trippy members going" badge on trip cards.
2
Community matchmaking — find a compatible travel companion
Happy path
Open Matches tab → see list of travellers ranked by compatibility score → tap a card → view full profile with score + AI explanation → "Send travel request" → optimistic UI "Request sent ✓" → mutual connection → chat unlocks → "Open chat" button appears.
Edge cases
No trip set: Full-screen "Set a trip first" state with destination search inline — don't make user navigate away. No matches yet: "You're early! Check back in [X days] or try ±3 day flexible dates." Incoming request while browsing: Toast notification + Matches badge pulse. Request declined: Quiet — no notification to the decliner (dignity UX). Both request each other simultaneously: Auto-accept as mutual connect.
Key components
MatchCard · ScorePill with explanation · VerifiedBadge · TrustStars · TravelRequestButton (5 states) · ChatLockedPreview · ReportBlockMenu
Improvements
Filter matches by: gender, travel style, budget range, verification status. "Wave" gesture (lighter than full request — no notification unless mutual). AI explanation always visible below score, not hidden in reasons list.
3
Hostel discovery — find where Trippy members are staying
Happy path
Open Hostels tab → set/inherit destination → see list with "X members staying" badges → tap hostel → see detail with member count + vibe tags → tap "Log my stay" → set check-in/out dates → becomes visible to other members (opt-in).
Edge cases
No hostels at destination: "No partner hostels in [destination] yet — suggest one" with a form. 0 members at hostel: Show "Be the first Trippy member here" instead of empty count. User hasn't set trip: "Set your destination to see member counts."
Key components
HostelCard · MemberCountBadge (with privacy toggle) · VibeTags · LogStayModal · HostelMemberList (opt-in visible members only)
Improvements
Privacy toggle: Explicit "Show me to other Trippy members at this hostel" checkbox on Log Stay — currently implied opt-in with no user control. Filter hostels by vibe (chill/social/party). Show Zostel/GoStops brand logos.
4
DIY trip path — build a self-organized adventure from scratch
Happy path
Tap "+" in bottom nav → choose "Build my own trip" → set destination + dates (if not set) → DIY overview with cost comparison → step 1: pick hostel → step 2: connect with people → step 3: form group + name it → Group Hub opens with shared itinerary, chat, expense tracker.
Edge cases
No connections for group: "Create group solo — invite people later" (already handled in code). Back navigation: Going back from step 2 preserves hostel selection (currently lost on re-mount). Group name empty: Disable create button (already implemented). Trip dates not set: DIY overview shows "flexible" cost — prompt to set dates for better matches.
Key components
DIYStepper · CostComparisonCard · HostelPicker · PeopleGrid · GroupFormCard · GroupCreatedSuccess
Improvements
State persistence: Save DIY progress to localStorage — "Resume your Spiti trip plan" on landing. Cost comparison: Make it the hero of the overview — large INR numbers, clear trade-off summary in 2 sentences. Navigation entry: "+" CTA in bottom nav must surface DIY as the self-serve option alongside "Browse trips."
5
DIY vs Group trip comparison — AI-generated cost trade-off
Happy path
From Results page → tap "Compare with DIY" → side-by-side: hosted trip all-inclusive price vs DIY breakdown (stay + transport + food + activities) → plain-language summary ("DIY saves ₹4,200 but requires more coordination") → user picks path → flows into either booking or DIY step 1.
Edge cases
No operator trips at destination: Show DIY breakdown only with "No group trips here yet — perfect for a DIY adventure." DIY more expensive: Frame as "The hosted trip saves ₹3,400 and handles logistics — worth considering." Never hide a number that goes against DIY.
Key components
ComparisonCard (2-column) · CostBreakdownRow · TradeOffSummary (plain language, 2 sentences) · PathCTA (hosted or DIY)
Improvements
Current implementation (DIY.tsx) puts comparison in the overview but it's text-heavy. Fix: Visual-first — large INR totals, color-coded rows (stay = teal, transport = coral, food = amber), and a single sentence trade-off. "Which is right for me?" should be answerable in 5 seconds without reading.
6
Hosted trip detail + Book Now
Happy path
From Results or discovery → tap trip card → Trip Detail page → read itinerary, includes, operator info → tap "Book Now" → redirect to partner's external payment page (new tab). Every click tracked.
Edge cases
Trip full: "Full" chip, Book Now disabled, "Join waitlist" option. Trip expired/past: "This trip has passed — see upcoming trips by [operator]" with operator link. External payment page 404: Can't detect (external), but show "Can't reach the booking page — contact [operator] directly" after 5s timeout on redirect attempt.
Key components
TripDetailHeader · ItineraryTimeline · IncludesExcludes · OperatorChip · BookNowButton (sticky on mobile) · AvailabilityBadge · "X Trippy members going" social proof
Improvements
Sticky Book Now bar: Fixed bottom bar on mobile with price + CTA (currently below fold). Social proof: "4 Trippy members have clicked Book Now" builds confidence. Share: "Share this trip" → native share sheet (copies URL).
7
Messaging — 1:1 and group chat
Happy path
Mutual connection established → Chat tab shows new DM → open thread → type + send → 3s polling delivers messages. Group: form DIY group → Group Hub opens group chat tab automatically.
Edge cases
Trying to chat before mutual connect: Profile shows locked chat preview — don't show chat option at all. Chat removed (403): Thread shows "This chat is no longer available" with back navigation. Image send (future): Placeholder: "Photos coming soon — share your Manali shots!" Long offline period: "You were offline for 3 days — 12 new messages" catch-up banner.
Key components
ChatLockedState · ChatThread · MessageBubble · PinnedBar · ReportFromChat (⋯ menu) · SafetyBanner (prominent, not 9px footer text)
Improvements
Pin → long-press: Mobile-standard gesture, not double-click. Safety banner: Move from 9px footer text to a collapsible yellow banner above message input (dismisses after 1 view). Unread badges: Show count on Chat tab in bottom nav. Typing indicator: "Priya is typing…" (Phase 2 with websockets).

DIY deep navigation — keeping the user from getting lost
The DIY path is a 4-step multi-screen flow inside the app. Key challenge: user is 2 steps into DIY, gets a match notification, switches to Matches tab, then returns — they've lost their place.

Solution: (1) Persist DIY state to localStorage as a "draft trip plan" object. (2) Show a "Resume your [Destination] plan" sticky card on the Discover landing if a draft exists. (3) The DIY stepper shows breadcrumb (Hostel ✓ → People → Group) — tapping completed steps doesn't reset them. (4) "Back" from DIY overview goes to Results, not the full back-stack (use navigate(-1) already done but needs the draft preservation).
Desktop / web sidebar
Current web app uses topnav (Matches · Requests · Chats · Hostels). Recommendation: Keep topnav for web, replace with bottom nav on mobile via CSS media query. The topnav on web should show: Discover · Matches (+ badge) · Chats (+ badge) · Hostels · [user chip]. "Requests" merges into Matches as a sub-tab. DIY accessible via Discover → Results → "Build your own" or via "+" action in both views.

08 — Search-first discovery

Design A — Landing → Results — two rails coexisting

The fundamental question: hosted trips (operator content) and DIY path (self-serve). How do they coexist without competing?

Recommended Results page structure
1. Header: "Trips to Spiti Valley · Aug 12–18 · [Edit]" · filter/sort row (Price · Dates · Type)
2. Hosted trips first — operator content is the primary discovery intent. Show as a vertical list (trip cards). Why first: users came from search with intent to find a curated trip. Label: "Group trips led by verified operators."
3. DIY path — shown as a distinct "card" between trip listings (after showing 2–3 operator trips). Not a sidebar, not a rail — a full-width interstitial card with coral accent. Headline: "Or build your own Spiti adventure — ₹8,200 estimated." One CTA: "Start DIY path →". This makes DIY a peer option without competing for visual hierarchy.
4. If 0 operator trips: DIY card moves to position 1 with messaging: "No operator trips for these dates yet — perfect for going your own way."
5. Comparison trigger: "See how DIY vs hosted trips compare" link below the DIY card → opens ComparisonModal.
Why not side-by-side tabs (Hosted / DIY)? Tabs create a binary choice before the user understands the difference. The interstitial card approach lets hosted trips do their job (most users want a curated trip) while surfacing DIY at the moment of consideration — not as a competing category but as "what if you can't find the right operator trip?"
09 — Future-proofing

Where Phase 2–4 features slot in without a redesign

AI chatbot (Phase 2)
Slots into Discover tab as an alternative search mode. SearchBar gets a toggle: "Search" vs "Ask AI." AI chat interface replaces the form-based searchbar — user types "I want a 5-day trek under ₹15,000 in October" → ranked trip results. No nav changes required. Also accessible from Group Hub as "AI itinerary suggestions" (already stubbed).
Trip Hub / in-trip OS (Phase 3)
Already exists as Group Hub (/groups/:id). Phase 3 expands it with: expense splitting tab, photo memory tab, live location tab. No nav changes — these are sub-tabs within Group Hub. The "+" CTA in bottom nav gains a third option: "My active trip" (if group exists with upcoming dates).
Social feed (Phase 3)
Replaces or augments the Discover tab with a feed sub-view. Toggle: "Trips" vs "Stories." Stories = post-trip photo logs from other travellers. Destination pages become social hubs. No new tab needed — Discover tab expands its scope. Follow/like features live on UserProfile (additional section) without displacing existing content.
Biker / road trip vertical (Phase 4)
New trip type filter on the Results page and a dedicated section on Landing ("Bikers heading to Leh →"). No new tab. DIY path gains a "Trip type" step (trek / bike / road trip / beach) which changes hostel suggestions and matching criteria. Could eventually become a sub-app but starts as a filter + dedicated onboarding question.
10 — Design checklist

25-point pre-handoff validation

Run this checklist on every screen before it leaves design. Three reviewers minimum: designer, product, and a traveller user.

Flow integrity (6 checks)
1
One primary CTA per screen. If there are two buttons, one must be clearly secondary (lower contrast, smaller size).
2
No dead ends. Every empty state has an action. Every error has a recovery CTA. Every success has a "next step" pointer.
3
Back navigation is always available and goes where the user expects. Wizard steps show a "Back" button. Deep flows preserve state on back.
4
Every async action has a loading state. Buttons disable + show spinner on tap. Lists show skeleton cards, not blank white.
5
Optimistic UI for trust-critical actions. Travel request sent → immediate "Sent ✓" state before server confirms. Never make the user wait to feel heard.
6
DIY path state is preserved if user switches tabs and returns. "Resume your plan" card appears on landing if draft exists.
Trust & safety (5 checks)
7
Compatibility score never appears alone. Always paired with a 1-sentence AI explanation ("Because you both love trekking and budget similarly").
8
Chat locked state is visible on every UserProfile where connection ≠ accepted. Lock icon + "Unlocks when you both connect" — never a broken button or a 403 error.
9
Report/block reachable in ≤2 taps from any profile, match card, or chat thread. The ⋯ menu must be visible without scrolling.
10
Hostel member count respects opt-in. Count (not names) shown by default. User's "Log my stay" shows explicit visibility toggle before saving.
11
Safety guidance is prominent, not a footnote. In chat: collapsible banner above input, not 9px footer text. First session: shown once on first DM open.
Empty + error states (4 checks)
12
Empty states explain WHY and WHAT TO DO. "No matches" → "You're early! [reason] · [action]". Never a bare "No results found."
13
Error messages are specific and actionable. "Something went wrong" is banned. Show what failed + what to try next. Form errors highlight the specific field.
14
New user empty states guide activation, not just inform. "Set a trip to see matches" must have the destination picker inline — not a link to another screen.
15
Network error states exist. Offline banner. Retry button on failed API calls. Chat input disabled with "Reconnecting…" when connection drops.
Mobile UX (5 checks)
16
All touch targets ≥44px. Especially chip toggles, nav icons, and profile action buttons. Test on actual 375px device — not just browser devtools.
17
Bottom nav safe area respected. No content hidden behind home indicator. Padding-bottom: 83px iOS / 48px Android on all scrollable content.
18
No horizontal scroll on mobile except intentional carousels with visual overflow affordance. Tables are replaced with card stacks below 640px.
19
Keyboard-aware layouts. Input forms don't get covered by the soft keyboard. Chat input stays above keyboard. Onboarding form scrolls correctly when keyboard appears.
20
Gestures are mobile-standard. Long-press (not double-tap) for context actions (pin message, report). Swipe-to-dismiss for bottom sheets. Pull-to-refresh on lists.
Copy clarity (5 checks)
21
No travel platitudes. "Start your adventure" and "Book your next journey" are banned. All CTAs are specific: "Find travellers going to Spiti", "Send travel request", "See your matches."
22
India-first copy. All prices in ₹. Destinations are Indian (Manali, Spiti, Goa, Ladakh). Examples use Indian names. Date format: DD MMM (not MM/DD).
23
Sentence case everywhere. Buttons: "Send travel request" not "Send Travel Request." Labels: "Travel style" not "Travel Style." Exception: proper nouns.
24
Matchmaking ≠ dating app language. No "swipe right", no "like", no heart icons on traveller profiles. It's a travel companion search. Language: "connect", "travel together", "request", "match."
25
Safety copy is warm, not legal. "Keep personal contact info private until you're comfortable — it's your call" not "Do not share personal information." Empowers the user; doesn't lecture them.
